## TL;DR

1. **怀疑成立，但方向需修正。** 43 项全绿 **不等于** 新列被覆盖 —— 实测确认：三条未批准增量
   （ER-11 埋点字典表 / ER-14 第三方绑定表 / CR-M2-001 权限矩阵）在断言侧 **新增覆盖 = 0**；
   其中 **`track_event_dict` 表从未进入 `02_schema.sql`**（全仓 `*.sql` 零命中），
   仅存在于设计文档 §7。
2. **只上 DDL 不同步断言 → 构建立即红。** 实测把两份补丁放进 `docker/mysql/init/` 后：
   `active_uk` **5 ≠ 3** ✗、`retain_until` **5 ≠ 4** ✗ → `失败 2 项`。
   → **DDL 与断言必须同批上库**，这是硬约束而非建议。
3. **3 条计数断言口径不同，风险不对称**：
   - `表总数` = **动态**（`grep -cE '^CREATE TABLE' DDL 文件`）→ 自动跟随，**但也无法发现"表缺失"**（自证式）；
   - `active_uk 数量` = **精确 3** → 加表即红（**脆**）；
   - `deleted 列` = **`≥ 19`** → 21 也通过，**对新增列完全不敏感**（**盲**）。
4. 结论：断言需 **+17 项**（ER-11 +3 / ER-14 +6 / CR-M2-001 +8），并同步改值 4 条计数断言。
   合并上库后断言总数 **43 → 60**。

## 一、基线事实（实测，非推断）

### 1.1 「43 项」是怎么来的

`verify-schema.sh` 的计数由**两类**构成，这一点此前未被明确记录：

| 来源 | 计数方式 | 基线数量 |
|---|---|---|
| `[1/7]` 初始化脚本逐个执行成功 | **每个 `.sql` 文件计 1 项** | **3**（`01_init` / `02_schema` / `03_seed_rbac`） |
| `[2/7]`–`[7/7]` 结构 / 数据 / 行为断言 | 每条 `check` / `check_ge` / `pass_msg` 计 1 项 | **40** |
| **合计** | | **43** |

> ⚠ **推论**：断言总数会**随 `docker/mysql/init/` 目录下 SQL 文件个数变化**。
> 补丁若以**独立文件**形式投入（如 `04_er11.sql`），会自动 +2；
> 若**并入 `02_schema.sql`**，则 +0。**因此"43 项"不是稳定常量，口径必须显式定格。**

### 1.2 基线运行结果（2026-09-21 复现）

```
[2/7] ✓ 表总数（与 DDL 定义数一致）        = 37
[3/7] ✓ 生成列 active_uk 数量              = 3
[6/7] ✓ ER-03 保留期列 retain_until（4 表） = 4
[6/7] ✓ ER-13 软删除列 deleted              = 19（≥ 19）
       ✓ 埋点留存控制列 expire_at（PRD §9 保留≤180 天） = 1（≥ 1）
[6/7] ✓ 权限点 sys_permission               = 16
       ✓ 角色-权限授权 sys_role_permission  = 23
       ✓ 敏感操作权限点 need_second_verify=1 = 3（≥ 2）
 结果：通过 43 项，失败 0 项
```

重跑 `verify-schema.sh`，观察哪些断言变化；随后**已删除临时文件并复跑还原**。

| 断言 | 基线 | 上补丁后 | 判定 | 说明 |
|---|---:|---:|---|---|
| 表总数 | 37 | **39** | ✓ 通过 | 动态取值，自动跟随；**但无法发现「表根本不存在」** |
| `active_uk` 生成列 | 3 | **5** | ✗ **失败** | 精确断言，**脆** |
| `retain_until` 列 | 4 | **5** | ✗ **失败** | 精确断言，**脆** |

## 三、43 项逐条覆盖对照（缺口定位）

| 域 | 现有断言 | 对三条增量的覆盖 |
|---|---|---|
| 表数量 | 1（动态） | **间接**：仅当 DDL 文件也缺失时才报警；单独缺表不报 |
| ADR-0003 全库口径 | 5（自增 / TIMESTAMP / DATETIME / 外键 / `deleted`） | **部分**：`active_uk` 精确值会红；`deleted` 因 `≥` 而盲 |
| 敏感字段密文 / 摘要 | 7 | 无覆盖（新表仅存 HMAC，未纳入断言） |
| 国标规则域播种 | 4 | 无关 |
| ER 补丁（03/04/05/06/07/08） | 6 | 无覆盖 |
| **埋点** | **1**（仅 `track_event.expire_at`） | **零覆盖 `track_event_dict`** —— 表不存在、无种子断言、无 `device_id` 禁采断言 |
| B2 RBAC 种子 | 8 | 4 条红线；**CR-M2-001 需 8 条**，缺 4 |
| 行为验证（软删除唯一键） | 5 | 仅覆盖 `elder_family_bind`；**未覆盖新表的 `active_uk` 行为** |
| **第三方绑定** | **0** | **完全不覆盖** |

**三个最危险的"看起来绿其实没查"项**：

1. `表总数` —— 自证式（DDL 文件与库内表同源），**无法发现"设计文档有表、DDL 没有"**。
   这正是 `track_event_dict` 的真实处境。
2. `deleted 列 ≥ 19` —— 用下界，**新增软删除表静默通过**；应改精确值或改为"每张业务表必须有 `deleted`"。
3. 埋点域仅 1 条断言 —— ER-11 定稿 30 事件 + 三级敏感 + 180 天留存，
   当前**一条都没验证**，`device_id` 禁采也无断言。

## 八、核查结论

- **用户判断成立**：43 项全绿**不能**证明改动后的列被覆盖；实测确认 `track_event_dict` 表在仓内 `*.sql` **零命中**。
- **但有两点需修正**：
  1. 不是「断言基于旧 DDL」这么简单 —— 是**三条增量整体未获批准、故未上库**；
     断言与 `02_schema.sql` 是**同步的**（都停留在已批准基线）。
  2. 「补断言」**不能单独做** —— 单独补会因表不存在而立刻红；必须 **DDL + 断言同批**。
- **已交付**：`ER-11-DDL-Patch-Proposal.sql`（建表 + 30 种子，apply-ready）、
  本合并口径表、ER-14 补丁按 PM 裁决更新（含 `retain_until`）、
  以及**实测证据**（上库后 39/5/21/5 全对，基线可复现 43 项全绿）。
