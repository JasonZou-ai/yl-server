# ADR-0006：报告 PDF 渲染选型 —— Apache PDFBox + 可插拔字体/存储

- 状态：**已接受**（2026-09-23）
- 决策者：研发侧（产品口径见 PRD P02「下载 PDF」/ 流程 A ④）
- 相关：ADR-0003（主键/时区/软删）、ADR-0004（定时任务）、C3 报告规则绑定、PRD §1.4 / §4.1 / P02

## 背景

C3 完成后，报告侧已绑定 `ruleVersion + 初判/终判/变化原因/规则指纹`，但**报告仍无实体文件**：
PRD 流程 A ④ 要求「生成报告 PDF + 二维码」，P02 操作区要求「下载 PDF / 分享」，家属端与监管上报都依赖可下载、可归档、可验真的 PDF。

同时本项目有两条既有红线，选型必须避开：

1. **许可红线**：iText 5/7 为 AGPL / 商业双许可，引入即传染（本项目为商业交付），不可接受；
2. **算分红线**：四端不做本地算分，PDF 内容必须由服务端按报告视图与照护方案渲染，不得端上拼装。

## 决策

**采用 Apache PDFBox 2.0.30（Apache-2.0）直接渲染矢量文本 PDF**，配套两条可插拔设计：

- **字体可插拔**：`yl.report.pdf.font-path` 显式指定中文字体（TTF/TTC）；留空时按系统常见字体探测；
  探测失败**降级渲染**（中文占位、`chineseEmbedded=false`）而**不阻断业务**——字体缺失属部署问题，改配置即可修复，不应让报告导出整体不可用。
- **存储可插拔**：MVP 落本地目录（`yl.report.pdf.dir`，默认 `${java.io.tmpdir}/yl-reports`），
  对象键固定为 `report/<reportNo>.pdf`；后续接腾讯云 COS 只需替换写入实现，键名与契约不变。

PDF 内容：标题与评估要素 → 等级判定三要素（初判/终判/变化原因）→ 4 维度得分（含拒答数）→ 照护建议 → 验真信息（规则版本、规则指纹、内容摘要、验真链接）。

## 备选与淘汰理由

| 方案 | 评估 |
|---|---|
| **PDFBox 直绘（选）** | Apache-2.0，无许可传染；零第三方服务依赖；矢量文本体积小、可检索、可归档；字体/存储均可插拔 |
| iText 7 / OpenPDF | iText 为 AGPL/商业双许可，商业交付场景下不可接受；OpenPDF 为 iText 4 分支（LGPL），生态与维护活跃度弱于 PDFBox |
| Flying Saucer（HTML→PDF） | 需额外引入 XHTML 渲染栈与中文字体注册，HTML/CSS 排版差异会导致报告版式随模板漂移，回归成本高 |
| 端侧生成 PDF | 直接违反「四端不做本地算分/不本地拼装报告」红线，且无法保证与服务端判定结果一致 |
| 只出 HTML 打印视图 | 无法满足「可归档、可验真 PDF」与监管上报诉求，仅可作为无字体环境的降级通道保留 |

## 由决策派生的约束

1. **中文字体必须可配置**：PDF 内置 14 种标准字体无中文字形，生产部署需在镜像中内置字体并通过 `yl.report.pdf.font-path` 指向；
   未配置且系统无字体时**降级渲染**，日志 WARN 提示，业务不中断。
2. **键名与 COS 形态一致**：`report/<reportNo>.pdf`。下载接口按报告编号取回，编号做 `[A-Za-z0-9_-]{1,64}` 白名单校验，防目录穿越。
3. **内容取自服务端**：等级、维度得分、照护建议均来自报告视图与 `care_plan`，PDF 不引入任何新的算分逻辑。
4. **验真锚点落 PDF**：规则版本、规则指纹、报告内容摘要（SHA-256）必须出现在验真章节，与二维码内容一致，支持事后复算比对。
5. **依赖版本在根 pom 统一**：`pdfbox.version` 走 `dependencyManagement`，模块 pom 不带版本号（与既有依赖管理方式一致）。

## 何时重新评估

- 需要**复杂版式**（表格分页、页眉页脚、图表雷达图内嵌）时，评估引入模板引擎 + Flying Saucer；
- 报告量上升需要**异步渲染 + COS 直传**时，替换存储实现并将渲染移入任务队列（ADR-0004 调度框架）；
- 出现**电子签章/骑缝章**合规要求时，重新评估 PDF 签名方案（PDFBox 支持 CMS 签名，但需密钥体系配合）。
