产品侧 · 8 项
  • P-1　PRD §3 的 24 个功能点是否「全部有表承载」——逐条核对 §5 映射表，确认 6 项 无表 与 3 项 部分承载 是否为预期

  • P-6　PRD §6 核心页面（P01 问卷 / P02 报告 / P03 工作台 / P04 绑定）所需字段能否全部从表中取到，有无「页面要展示但库里没有」的字段
  • P-7　PRD §3 功能点 2 的 4 维度命名是否以国标为准回写 ER-01
  • P-8　PRD §1.2 本期范围是否显式声明「消息中心」「支付与合同」的取舍 ER-02
研发侧 · 10 项
  • D-1　主键生成策略：业务表主键均为 BIGINT NOT NULL（无 AUTO_INCREMENT），须由应用层分布式 ID 赋值；而 01_init.sql 的 gb_rule_version 用了自增 —— 两套并存是否有意 ER-09
  • D-2　引用完整性：全库 0 个外键约束，靠应用层保障。确认此为有意选择，并写入编码规范（否则多人协作下会出现悬空引用）ER-13
  • D-3　时区策略：全库时间列均为 DATETIME（51 处）、0 处 TIMESTAMP，无时区语义，取值依赖数据库/会话时区；生产容器 TZ 须固定 ER-12
  • D-4　并发控制：eval_order / eval_answer 无版本号列，而 PRD §7 要求幂等防重、§4.3 要求离线冲突提示 ER-05
  • D-5　事务边界：一次「提交复核」涉及 eval_order 状态 + 26 行 eval_answer + eval_review_log，须单事务；报告生成与 eval_report 的写入时序须明确
  • D-6　幂等一致性：Redis（SET NX EX）与 idempotent_record 兜底表的写库时机与失败补偿路径须明确
  • D-7　索引复核：108 个索引中是否存在冗余（前缀重复）或缺失（如报告按 verify_hash 验真、审计按操作人 + 时间）
  • D-8　软删除一致性：33 张表 deleted 是否统一，查询侧是否由全局逻辑删除统一过滤（避免个别查询漏过滤导致已删除数据泄露）
  • D-9　大表治理：track_event 高频写入，180 天清理由 XXL-JOB 执行；确认何时需要改按月分区
  • D-10　字符集与排序规则：建库指定 utf8mb4_unicode_ci，表级未显式声明（继承库默认）。确认是否统一为 MySQL 8 默认 utf8mb4_0900_ai_ci（性能更优）或以 unicode_ci 为准
合规侧 · 10 项
  • C-1　个人信息分类分级清单：身份证号／真实姓名／手机号／住址／健康史／用药记录，逐项定级（一般 vs 敏感个人信息），形成表格式清单入档
  • C-2　人脸信息：仅存 COS 对象键、不落原始图像 ✓；但人脸属敏感个人信息，须确认「单独同意」的取得方式与存储地域在境内
  • C-3　加密方案：AES-256-GCM + 主密钥经 KMS 托管、SENSITIVE_FIELD_KEY 环境变量注入、密钥缺失即启动失败 ✓；确认密钥轮换周期与责任方
  • C-4　检索摘要（HMAC-SHA256）与加密密钥分离 ✓；确认摘要列本身不构成可反推的个人信息
  • C-5　保留期：埋点 ≤180 天 ✓ 已落 expire_at；审计日志、监管报表、评估记录的保留期均未定义 ER-03
  • C-6　二次验证：导出／删除／作废／解绑 四类敏感操作需二次验证并留痕 ✓；确认验证方式（短信／人脸）与失败处理
  • C-7　最小必要：埋点 params 仅存 ID 与枚举 ✓；org.contact_name 明文是否需要加密 ER-10
  • C-8　数据出境：确认 COS 存储地域在境内、无境外传输路径
  • C-9　告知同意留痕：现有 elder_authorization（档案授权）与 elder_family_bind（亲情绑定）两张授权表，但无「隐私政策告知同意」的版本与时间留痕 ER-08
  • C-10　日志脱敏：加密仅作用于入库路径；确认应用日志（MDC/异常堆栈）不会打印明文敏感字段，须有代码层约束与检查
